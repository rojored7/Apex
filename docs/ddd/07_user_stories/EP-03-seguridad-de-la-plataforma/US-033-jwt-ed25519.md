# US-033 · Como equipo quiero emitir y validar JWT firmados con Ed25519 de 15 minutos y refresh tokens opacos de 7 días para que una sesión robada dure poco y un token manipulado nunca pase

- **Épica:** EP-03 · Seguridad de la plataforma
- **Bounded context:** `core/security`
- **Versión:** v0.1
- **Actor:** equipo
- **Tamaño:** 3
- **Prioridad:** P0 ruta crítica
- **Refinamiento:** Lista para sprint
- **Pantalla:** Ninguna (historia sin front)

## Historia

Como equipo
quiero `create_access_token(user)`, `decode_access_token(token)` y `new_refresh_token()` en `core/security.py`
para que Auth emita sesiones cortas firmadas con una llave que nunca está en la imagen y rechace cualquier token vencido, ajeno o con algoritmo cambiado

## Contexto de dominio

- **Aggregate / entidades:** `User`, `RefreshToken` (la tabla y la revocación son de US-041 y US-043).
- **Reglas que aplica:** `CLAUDE.md` Seguridad (JWT Ed25519, 15 minutos, refresh 7 días con revocación); `04_architecture_decision.md` sección 6 (llaves por volumen); RN-15.
- **Eventos que emite:** ninguno
- **Eventos que consume:** ninguno
- **Funciones puras:** `security.access_claims(user, now) -> dict` (claims: `sub`, `role`, `member_id`, `iat`, `exp`, `jti`)

## Alcance

- **Backend:** firma con PyJWT y algoritmo fijo `EdDSA`; llave privada desde `JWT_PRIVATE_KEY_PATH` (volumen, 600) y pública derivada. `decode` acepta solo `algorithms=["EdDSA"]`, exige `exp`, `iat`, `sub` y `role`, y tolera 30 segundos de desfase. `new_refresh_token()` devuelve un valor aleatorio de 32 bytes en base64url y su hash SHA-256 para guardar (nunca se guarda el token en claro). Vidas desde configuración: 15 minutos y 7 días. Usa `Clock` (US-013) para probar vencimientos.
- **Front:** No aplica

## Criterios de aceptación

1. Un access token emitido tiene `exp - iat = 900` segundos y `role` igual al del usuario.
2. `decode_access_token` de un token vencido lanza `TokenExpired`.
3. Un token firmado con otra llave Ed25519 lanza `TokenInvalid`.
4. Un token con cabecera `alg: none` o `alg: HS256` firmado con la llave pública como secreto lanza `TokenInvalid` (prueba de "alg confusion").
5. Un token sin `role` o con un `role` fuera de `admin`, `coach`, `member` lanza `TokenInvalid`.
6. `new_refresh_token()` devuelve token y hash; el hash es lo único que se persiste y el token tiene al menos 256 bits de entropía.
7. Si `JWT_PRIVATE_KEY_PATH` no existe, el arranque falla con mensaje explícito.
8. Ningún token aparece en los logs (prueba de captura).
