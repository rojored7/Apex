**Qué necesita un `OpenBaoProvider`** (`core/crypto/openbao_provider.py`, único sitio con `httpx` contra OpenBao): `httpx.AsyncClient` con timeout (`OPENBAO_TIMEOUT_S`) y cabecera `X-Vault-Token` leída de `OPENBAO_TOKEN_PATH` (token periódico renovado con `auth/token/renew-self`); `wrap(key_ref, dek)` = `POST /v1/transit/encrypt/apex-kek-<data_class>` con `plaintext` en base64, guardando el texto `vault:v1:...` como bytes en `wrapped_material`; `unwrap` = `decrypt`; para distinguir `sealed` de `unreachable`, `GET /v1/sys/seal-status` (no necesita token); 503 con sellado → `CryptoSealed`, 403 → `CryptoForbidden`, timeout o red → `CryptoUnreachable`; el token y la URL nunca en logs ni excepciones (`test_no_sensitive_in_logs`). La política del token debe cubrir `encrypt`, `decrypt`, `sign`, `verify`, `keys/*/rotate`, lectura de `keys/*` y `renew-self`. Sin TLS en la red interna en v0.2.

## 2. Mapeo del entorno de ejecución

- **api (desarrollo)**: `apex-api-1` con `api/src` y `api/migrations` montados y `uvicorn --reload` con polling (`compose.dev.yml`); migra al arrancar (`MIGRATE_ON_STARTUP=true`); una migración nueva exige `restart api` (el hot reload no vuelve a ejecutar el `lifespan`).
- **worker (desarrollo)**: `api/src` de solo lectura y SIN `--reload`: todo cambio en `app/worker/` o en un service que use un job exige `restart worker`; `notify` y `notifications/service.py` caen aquí.
- **tools**: sin bind de código en producción, `ro` en desarrollo; `migrate-provider` se ejecuta con el propietario (`docker compose run --rm tools migrate-provider ...`), no con `apex_api`.
- **Producción por COPY**: `apex-api:local` único para `api`, `worker`, `tools` y `migrate`; reconstruir con `buildx` y `--network host` (`docker compose build` roto en este equipo, RUNBOOK §7). `apex-web:local` estático servido por Nginx. El servicio `openbao` usa una imagen externa sin build: necesita `docker pull` en el host.
- **Cadena de arranque** (`compose.yml`): db → migrate → dbsetup → api → worker y web; `backup` tras dbsetup. `openbao` debe arrancar antes que api y worker, pero un `depends_on: service_healthy` de OpenBao sellado bloquea el arranque; su healthcheck (`bao status`) devuelve 0 si está abierto y 2 si está sellado, y ese 2 no es fallo de proceso.
- **Salida a internet**: no verificada desde los contenedores (compose.dev.yml advierte que el puente de WSL2 puede quedar sin salida); SMTP, Brevo y Telegram se prueban con Mailpit y `httpx.MockTransport` en desarrollo; la prueba en vivo es de producción.
- **Nginx**: sin zonas nuevas para las rutas nuevas; el CSV no se bufferiza si el api envía por chunks (`proxy_read_timeout 60s` es por lectura, no total).
- **`.env` real**: `env_file ../.env` llega completo a api, worker y tools. En el repositorio solo existe `.env.ops.example`.
- **Bugs de configuración que bloquean**: (a) healthcheck del api solo 200 + `depends_on service_healthy` en `web` y `worker` + `curl -f` en `deploy.sh`, frente a `crypto` crítico (hallazgo 4); (b) `validate_crypto_provider` y `missing_secrets` (`config.py:549`) no conocen `openbao`: una configuración válida de OpenBao exigiría hoy `CRYPTO_LOCAL_KEK_PATH`; (c) `bootstrap.py:63` `provider="local"` literal; (d) `test_compose_config.sh` fija los volúmenes exactos del worker y, en desarrollo, `depende(dev, svc) == {"db"}` para api y worker (un `depends_on: openbao` lo rompe); (e) `alembic.ini` está bien (`file_template %(rev)s_%(slug)s`): el siguiente id es `0015`, no `0030`.
