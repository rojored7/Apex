## 1. HIGH
### H-1 · `migrate-provider`, `rotate-kek` y el retiro de la KEK local no exigen un snapshot de OpenBao verificado y emparejado (D8, D18, D19, B13)
Riesgo: tras migrar, `crypto_keys.wrapped_material` solo abre con el `apex-kek` del volumen `openbao-data`, un nodo raft único. D8 deja B13 como "si cabe" y D18 solo "recuerda" el respaldo. Si el volumen se pierde justo después de migrar o de rotar (dump nuevo con `vault:v2`, snapshot viejo solo con v1) se pierden todos los datos personales cifrados: la KEK local ya se retiró y las llaves de desello no sirven sin los datos. Además `bootstrap.sh` "crea `apex-kek` si falta": sobre un volumen vacío fabrica una llave nueva en silencio y oculta la pérdida.
Corrección (S5-D49): (1) B13 es bloqueante: `migrate-provider` (sin `--dry-run`), `rotate-kek` y `retire-local-kek` leen `latest.json` firmado y exigen `openbao_snapshot` con `verified=true` de menos de 24 h; si no, salen 2. (2) `rotate-kek` termina disparando una corrida de `backup`; el RUNBOOK dice que dump y snapshot se restauran en pareja. (3) `bootstrap.sh` crea `apex-kek` solo con `--first-install` y confirmación escrita; en un volumen vacío sin ella aborta con "volumen de OpenBao vacío: restaurar snapshot". (4) `restore_e2e` de OpenBao: snapshot restaurado, desellado y `--verify` en verde. Slices W0-2, B2, B13.
### H-2 · La KEK local sigue montada en api y worker tras migrar: OpenBao no separa nada mientras `kek.bin` esté en el servidor (D3, D18, D20, `compose.yml` api `keys:ro`)
Riesgo: D18 deja el retiro como paso humano del RUNBOOK; `compose.yml` monta `keys:ro` en el api y D20 en el worker. Un RCE en el api lee `kek.bin` y, con cualquier volcado, descifra todo: el valor de seguridad del sprint es nulo si el paso se olvida. Las filas `sign` siguen `local` (D9), así que el proveedor local puede seguir construyéndose y pidiendo el archivo.
Corrección (S5-D50): (1) overlay `compose.openbao.yml` en que api y worker no montan `keys`; `tools` sí, hasta `retire-local-kek`. (2) `cli retire-local-kek --as`: exige `migrate-provider --verify` en 0, `verify-kek-backup` de menos de 24 h y snapshot (H-1); mueve `kek.bin` fuera del volumen servido y registra `crypto_ops` y auditoría. (3) `prod-smoke.sh` con `CRYPTO_PROVIDER=openbao` comprueba que `kek.bin` no existe en api ni worker; una prueba de B1 arranca el api sin `kek.bin` con una fila `sign` local (resolución perezosa, solo `unwrap` de filas `encrypt` e `index`). (4) `deploy.sh` avisa si `CRYPTO_PROVIDER=openbao` y `kek.bin` sigue en `keys`. Slices B1, B2, W0-2.
